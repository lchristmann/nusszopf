# Authorization Matrix

This is the single, explicit answer to "who is allowed to do X" for Nusszopf 2. It consolidates
`docs/domain/permissions.md` (the historical Hasura enforcement, which is the evidence base) and
`docs/authentication/README.md` (route-level access) into one cross-cutting table, and maps every
row to the Laravel authorization primitive that must enforce it in the rewrite.

Per `.claude/rules/04-evidence.md`, backend/Hasura permission evidence is authoritative for what
was actually enforced; a frontend UI restriction that isn't mirrored here is advisory only, never
a security boundary, and must not be treated as one in the rewrite either.

**Two roles exist historically, and only two exist in Nusszopf 2**: `anonymous` (guest/unauthenticated)
and `user` (any authenticated account). There is no staff/admin/moderator role anywhere in the
historical evidence (`docs/domain/entities.md`, "Entities confirmed absent"). Do not introduce one
without new, explicit, approved evidence — see `CLAUDE.md`'s "Never" list.

## How to read this table

- **Rule** is the exact condition, not "should be protected" — copy it into the Policy method body.
- **Historical status** is Confirmed/Fix/Gap per `docs/rewrite/intentional-changes.md`. A row marked
  **Fix** reproduces the *intent*, not the historical enforcement — see the linked intentional-change
  entry for what actually changes.
- **Nusszopf 2 enforcement** names the concrete Laravel mechanism. `Policy` = a method on the
  resource's `Illuminate\Auth\Access\Policy` class, checked via `$this->authorize(...)`/`@can`.
  `Scope` = an Eloquent query scope applied to every read path (list, search, direct show), not
  just a controller-level gate, so a private resource can never leak via a differently-shaped query.

## Analytics (view/contact counters)

Already covered under **Project** above. Restated because the task explicitly calls it out: the
historical implementation had **no authorization at all** on these two counters (any caller,
authenticated or not, could set either counter to an arbitrary value for any project, including
private ones they don't own). Nusszopf 2 closes this by never exposing them as directly writable
fields through any authorization boundary — they are incremented exclusively by server-side
controller logic triggered by an actual page view / actual contact action, with no user-facing
"write views" ability to authorize in the first place.

## Direct URLs / mutations / API endpoints

There is no historical public GraphQL/REST API surface intended for third-party consumption — every
historical Hasura permission exists to serve the `webapp` frontend itself, not an external API
product (`docs/architecture/mapping.md`). Nusszopf 2 has no client-side data-fetching layer that
needs an equivalent public API (Livewire talks to Eloquent server-side), so this concern collapses
into the same Policy/Scope enforcement as every other row in this table — there is no separate
"API authorization" surface to design. If a public API is ever added, it is a new product decision,
not a historical requirement, and needs its own authorization design at that time.

## What this table does not cover

- Rate limiting (see `docs/security/README.md`, "Rate limiting" — historically absent everywhere,
  a fresh decision for Nusszopf 2, not a port).
- CSRF (Laravel's default protection applies uniformly; no historical equivalent to translate since
  the historical frontend was a client-rendered SPA calling a GraphQL API with a bearer token, not a
  form-posting server-rendered app).
- Session/cookie security specifics — see `docs/authentication/README.md`.
